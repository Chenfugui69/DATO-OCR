# 09 · 第二阶段：账号与 iPhone 同步

> **第一版不实现这个模块。**
> 第一版只需要做第 6 节「预留」里的事——在数据库里留好字段，别的都不用管。
> 这份文档是给未来启动第二阶段时看的，现在写下来是为了避免第一版做出无法扩展的结构。

---

## 1. 先说清楚能做什么、不能做什么

### 1.1 不能做的

| 想法 | 为什么不行 |
|---|---|
| 接入苹果的「隔空剪贴板」（Universal Clipboard） | 这是苹果私有的、基于 Handoff/Continuity 的系统级功能，只在苹果设备之间通过 BLE + WiFi 直连实现，协议未公开，没有任何开放接口。Windows 上无法接入 |
| 用 iCloud 存剪贴板数据 | CloudKit 的 Web Services 确实能在非苹果平台访问，但它要求数据的写入方也在苹果生态里。而且 CloudKit 的容器绑定 App ID，Windows 端拿不到合法的身份令牌 |
| 用「Sign in with Apple」登录后就能同步 | Sign in with Apple 只是一个 OAuth/OIDC 身份提供方，它只回答"这个人是谁"，不提供任何存储能力 |
| 在 Windows 上直接读 iPhone 的短信 | iOS 完全沙盒化，第三方 App 都读不到短信，更不用说 Windows |

### 1.2 能做的

**唯一可行的架构是自建：**

```
┌─────────────┐                    ┌──────────────┐                  ┌─────────────┐
│   iPhone    │                    │   我们的      │                  │   Windows   │
│ CHENOCR App │ ──── 加密上传 ───→ │   服务器      │ ──── 推送 ────→ │   CHENOCR   │
│             │ ←─── 拉取 ────────  │              │ ←─── 上传 ────── │             │
└─────────────┘                    └──────────────┘                  └─────────────┘
      │                                                                      
      └─ 用户手动复制 → App 读剪贴板 → 上传
      └─ 收到验证码短信 → 用户在通知里点一下 → App 转发
```

**关于验证码的重要限制**：iOS 上第三方 App **无法自动读取短信**。可行的做法只有两种：

1. **共享（Share Sheet）** —— 用户在信息 App 里长按验证码 →「拷贝」→ 切到 CHENOCR App（或用快捷指令自动化）。半自动
2. **快捷指令自动化** —— iOS 的「快捷指令」App 支持「收到信息时」的自动化触发，可以调用我们 App 的 URL Scheme 把内容传过来。**用户需要自己配置一次**，配好后是全自动的。这是目前唯一真正自动的路径，很多同类工具（如 Pushbullet 的替代品）都是这么做的

**必须在产品页面明确告知用户这个限制**，不要让人以为装上就自动收验证码。

## 2. 三种方案对比

| | A · 完整云同步 | B · 局域网直连 | C · 混合 |
|---|---|---|---|
| 出门在外能同步 | ✅ | ❌ | ✅ |
| 需要服务器 | ✅ 30–100 元/月 | ❌ | ✅ |
| 需要苹果开发者账号 | ✅ 688 元/年 | ✅ 688 元/年 | ✅ |
| App Store 审核难度 | 中（涉及账号和云存储，要写隐私政策） | 低（纯本地功能） | 中 |
| iOS 后台限制影响 | 小（用推送唤醒） | 大（后台连不上会断） | 小 |
| 开发量 | iOS 3–4 周 + 服务端 2–3 周 + Win 1 周 | iOS 2 周 + Win 1 周 | 上述之和 |
| 隐私 | 数据过服务器（但端到端加密后服务器看不到明文） | 数据不出家门 | 可选 |

**建议：先做 B，再升级到 C。** 局域网版可以快速验证整个交互是否好用，且不用先掏服务器和审核的成本。

## 3. 方案 A：完整云同步的设计

### 3.1 账号体系

**登录方式**：Sign in with Apple 为主，邮箱 + 密码为辅。

- Sign in with Apple 在 Windows 上走 **Web 流程**：在系统浏览器里打开 `appleid.apple.com/auth/authorize`，用户授权后回调到我们的服务器，服务器换取 token，再通过一个一次性的配对码回传给桌面端
- 注意苹果会返回一个**每个 App 唯一的匿名用户 ID**，且用户可以选择隐藏真实邮箱（苹果会给一个中转邮箱）。设计时不要依赖真实邮箱作为主键
- 苹果要求：**如果 App 提供了任何第三方登录，就必须同时提供 Sign in with Apple**。反过来不强制。所以只做邮箱登录也是合规的

**设备管理**：
- 每台设备有一个 `device_id`（Windows 用机器 GUID 的哈希，iOS 用 `identifierForVendor`）
- 用户可以在设置里看到所有已登录设备，可以远程踢掉某台
- 每台设备有独立的令牌，踢掉一台不影响其他

### 3.2 端到端加密

**服务器绝对不能看到剪贴板明文。** 这是必须的，剪贴板里可能有密码、身份证号、私钥。

密钥方案：

```
用户主密码（不是登录密码，是单独设的「同步密码」）
        │
        ├─ Argon2id (memory=64MB, iterations=3, parallelism=4)
        ↓
    主密钥 MK (32 bytes)   —— 只存在于用户设备上，永不上传
        │
        ├─ HKDF-SHA256 派生
        ↓
    数据密钥 DK
        │
        ↓
   AES-256-GCM 加密每一条剪贴板内容
```

- 盐（salt）存在服务器上（盐不是秘密），用户在新设备登录时下载盐 + 输入同步密码 → 本地重新派生出同样的密钥
- **忘记同步密码 = 数据无法恢复**。必须在设置密码时用醒目的方式告知，并提供导出恢复码的选项
- 每条内容用独立的随机 nonce（12 bytes），不要复用

⚠ 不要自己实现密码学。用 `ring` 或 `age` crate（Rust）、CryptoKit（iOS）。

### 3.3 服务端

最小可行的技术栈：

| 组件 | 选型 | 理由 |
|---|---|---|
| 语言 | Rust (axum) 或 Go | 单二进制部署，资源占用小，一台 2 核 2G 能撑几千用户 |
| 数据库 | PostgreSQL | 需要事务和 JSON 字段 |
| 对象存储 | S3 兼容（阿里 OSS / Cloudflare R2） | 存加密后的图片 |
| 实时推送 | WebSocket（在线时）+ APNs（iOS 离线时） | |
| 部署 | Docker + 单机，先不上 K8s | |

**API 设计**（REST + WebSocket）：

```
POST   /v1/auth/apple             Sign in with Apple 回调
POST   /v1/auth/refresh           刷新令牌
GET    /v1/devices                设备列表
DELETE /v1/devices/{id}           踢掉设备

POST   /v1/sync/push              上传变更（批量）
GET    /v1/sync/pull?since={rev}  拉取变更（增量）
POST   /v1/blobs                  上传加密后的图片，返回 blob_id
GET    /v1/blobs/{id}             下载

WS     /v1/stream                 实时推送变更通知（只推 "有新数据"，不推内容）
```

**同步模型**：基于**单调递增的服务器版本号（revision）**，不是时间戳（时间戳有时钟不同步问题）。

```
每次 push，服务器分配一个全局递增的 rev
客户端记住自己拉到的最大 rev
pull 时带上 since=最大rev，服务器返回之后的所有变更
```

**冲突处理**：剪贴板是"追加为主"的数据，冲突极少。规则：

- 新增：按 `sync_id`（客户端生成的 UUID）去重，重复的丢弃
- 修改（置顶/收藏/备注）：**后写胜出**（Last-Write-Wins），比较 `sync_rev`
- 删除：软删除，存一条 tombstone 记录，30 天后物理删除

**配额**：免费用户 500 条 / 100 MB blob，超出后停止上传并提示。

### 3.4 iOS App

**功能范围要极简**，它不是一个完整的 CHENOCR，只是一个同步端：

- 剪贴板历史列表（能查看、复制、删除）
- 手动上传当前剪贴板（一个大按钮 + 一个小组件 + 一个快捷指令动作）
- 接收电脑端的剪贴板（推送通知，点开即复制）
- 验证码转发（通过快捷指令自动化）
- 设置：登录、同步密码、设备管理

**技术要点**：

- SwiftUI，最低支持 iOS 16
- **iOS 不允许后台持续监听剪贴板**。iOS 14 起，读剪贴板还会弹出"XX 粘贴自 XX"的提示。所以自动上传是不可能的，必须由用户触发
- 三种触发方式：
  1. 打开 App（前台时可以读剪贴板）
  2. 主屏小组件上点一下
  3. **快捷指令动作**（推荐主推这个）—— 我们提供一个 App Intent「上传剪贴板到 CHENOCR」，用户可以把它绑到「轻点背面两下」或者自动化上
- 接收方向可以做到自动：电脑复制 → 服务器推 APNs → iOS 在后台把内容写入剪贴板。**但 iOS 后台写剪贴板也有限制**，静默推送唤醒 App 的时机不保证。实际做法是发一条可见通知，用户点一下就复制

**验证码自动转发的完整配置流程**（要写成 App 内的引导）：

```
1. 打开「快捷指令」App → 自动化 → 新建
2. 选择「信息」触发器，条件：信息包含「验证码」或「code」
3. 添加动作：CHENOCR「转发内容」
4. 关闭「运行前询问」
5. 完成
```

### 3.5 Windows 端改动

第一版留好的字段直接派上用场：

- `sync_id` / `sync_rev` / `sync_state` / `device_id` 已经在表里
- 新增一个后台同步任务：
  - 启动时全量 pull 一次
  - 之后维持 WebSocket 长连接，收到通知就 pull 增量
  - 本地有变更时（`sync_state = 1`）批量 push，防抖 2 秒
  - 断线指数退避重连（1s → 2s → 4s → ... → 60s 上限）
- 设置页新增「账号」分组

**验证码提示的界面**：收到标记为验证码的内容时，在屏幕右上角弹一个特殊的卡片：

```
┌──────────────────────────────┐
│  📱 来自 iPhone 的验证码       │
│                              │
│       8 4 2 7 1 9            │  ← 大字号等宽，字间距拉开
│                              │
│  [复制]        淘宝 · 刚刚    │
└──────────────────────────────┘
```

- 自动复制到剪贴板（可在设置里关闭）
- 12 秒后自动消失
- 用正则从短信里提取纯数字验证码：`(?:验证码|code|OTP)[^\d]{0,10}(\d{4,8})` 以及 `(\d{4,8})[^\d]{0,10}(?:验证码|code)`

## 4. 方案 B：局域网直连的设计

**更适合先做。** 没有服务器、没有账号、没有云存储，审核也简单。

### 4.1 发现机制

用 mDNS / Bonjour（`_chenocr._tcp.local`）在局域网里互相发现。

- Windows 端：`mdns-sd` crate 广播服务
- iOS 端：`NWBrowser`（Network framework）浏览
- 首次连接需要**配对**：Windows 端显示一个 6 位数字，用户在 iPhone 上输入，双方交换长期公钥

### 4.2 传输

- TLS，但用**自签证书 + 证书固定**（配对时交换的公钥就是固定的锚点）
- 或者更简单：用 Noise Protocol（`snow` crate）做加密通道，配对时交换的密钥直接用
- 传输层用 WebSocket 或裸 TCP + 长度前缀的消息帧

### 4.3 iOS 后台的现实

- iOS App 进入后台后，网络连接会在几十秒内被系统断开
- 所以**电脑 → 手机**方向在手机锁屏时基本不可用
- **手机 → 电脑**方向没问题（用户主动打开 App 或用快捷指令触发时是前台）
- 缓解：iOS 端可以申请 `Local Network` 权限 + 使用 `NEAppPushProvider`（但那需要企业级的特殊 entitlement，个人开发者拿不到）

**结论**：局域网方案适合"手机 → 电脑"单向，比如把手机上复制的东西发到电脑。反向要靠云推送。这也是建议最终走混合方案 C 的原因。

## 6. 第一版必须预留的东西

**这是第一版唯一需要为第二阶段做的事，其他都不用管。**

### 6.1 数据库字段（已在 `07` 的 schema 里）

```sql
-- clipboard_items 表已包含：
sync_id     TEXT,                        -- 客户端生成的 UUID，全局唯一
sync_rev    INTEGER NOT NULL DEFAULT 0,  -- 服务器版本号
sync_state  INTEGER NOT NULL DEFAULT 0,  -- 0=纯本地 1=待上传 2=已同步 3=待删除
device_id   TEXT                         -- 这条记录来自哪台设备

CREATE INDEX idx_clip_sync ON clipboard_items(sync_state) WHERE sync_state = 1;
```

**第一版的行为**：插入记录时给 `sync_id` 填一个 UUID，`device_id` 填本机 ID，`sync_state` 恒为 0。其余不动。

### 6.2 tombstone 表

第一版就建，但不用：

```sql
CREATE TABLE sync_tombstones (
  sync_id    TEXT PRIMARY KEY,
  deleted_at INTEGER NOT NULL,
  device_id  TEXT NOT NULL,
  sync_rev   INTEGER NOT NULL DEFAULT 0,
  sync_state INTEGER NOT NULL DEFAULT 0
);
```

第一版删除剪贴板条目时，**同时往这张表插一条记录**。这样以后开启同步，删除操作能正确传播。tombstone 保留 90 天后自行清理。

### 6.3 设备 ID

第一版启动时生成一次并持久化：

```
device_id = base32(sha256(机器GUID + 用户SID)[..10])
```

存在 `settings.json` 里。这样以后接同步时设备身份是延续的。

### 6.4 设置页占位

设置页里加一个「账号」分组，内容是：

```
  账号
  ┌────────────────────────────────────────────────┐
  │  多设备同步                                     │
  │  即将推出。可在电脑和 iPhone 之间同步剪贴板。    │
  └────────────────────────────────────────────────┘
```

不要做假的登录按钮，就一句说明。

### 6.5 架构上的注意

- 剪贴板的**写入操作全部走一个统一的仓储层**（`storage/clipboard_repo.rs`），不要在多处直接写 SQL。以后加同步逻辑只需要改这一个地方
- 图片文件名用 UUID，不要用自增 ID 命名。以后同步时文件名要跨设备唯一
- 所有时间戳存 **Unix 毫秒（UTC）**，不存本地时间

## 7. 启动第二阶段前要确认的事

按这个顺序确认，任何一条否定就先别启动：

1. 第一版已经稳定运行至少一个月，没有 P0/P1 缺陷
2. 已经有实际用户在用，且有人明确提出了同步需求
3. 愿意承担每年约 2500 元的固定成本（开发者账号 + 服务器）
4. 接受 App Store 审核可能反复被打回，上架时间不可控
5. 想清楚了忘记同步密码 = 数据无法恢复这件事，并接受为此提供客服支持
6. 决定好了走 A / B / C 哪个方案
