# 02 · 截图模块

> 本项目最核心的模块。第 3 节的交互清单是逐条验收项，**每一条都不允许打折**。
> 适用阶段：M1、M2。

---

## 1. 整体流程

```
用户按下 F1
   │
   ├─ [Rust] 立即 capture_prepare()
   │    ├─ xcap 抓取全部显示器画面 → 存到临时目录
   │    ├─ 枚举全部可见窗口的矩形 + Z 序 + 进程名
   │    └─ 返回给前端
   │        ⚠ 这一步必须在任何窗口显示之前完成，否则会拍到自己
   │
   ├─ [Rust] 为每个显示器创建一个 capture-{id} 窗口
   │    覆盖该显示器的完整物理区域，透明、无边框、置顶、跳过任务栏
   │
   ├─ [前端] 各窗口渲染本显示器的画面为背景
   │    整体压暗遮罩 → 进入「自动检测态」
   │
   ├─ 自动检测态 ──(鼠标按下拖拽)──→ 自由框选态
   │      │                              │
   │      └──(点击某个高亮窗口)──────────┤
   │                                     ↓
   │                                 编辑态（工具条出现）
   │                                     │
   │                    ┌────────────────┼────────────────┐
   │                    ↓                ↓                ↓
   │                 标注绘制        调整选区        执行动作
   │                                                      │
   └──────────────────────────────────────────────────────┤
                                                          ↓
                          复制 / 保存 / 贴图 / 识字 / 翻译 / 长截图
                                                          ↓
                                              关闭所有 capture 窗口
```

## 2. 抓屏与坐标系（最容易出 bug 的地方，先读透）

### 2.1 三套坐标

任何时候都要清楚当前用的是哪一套：

| 坐标系 | 定义 | 用在哪 |
|---|---|---|
| **物理像素坐标（Physical）** | 以主显示器左上角为原点，单位是真实像素 | xcap 抓到的图、Win32 API 返回的窗口矩形、最终裁剪 |
| **逻辑坐标（Logical）** | 物理坐标 ÷ 该显示器的缩放因子 | Tauri 的窗口位置 API、鼠标事件 |
| **窗口内 CSS 坐标** | 以当前 capture 窗口左上角为原点，CSS 像素 | 前端所有绘制、鼠标事件 |

### 2.2 换算规则

```
物理坐标 = 窗口物理原点 + CSS坐标 × devicePixelRatio
CSS坐标  = (物理坐标 - 窗口物理原点) / devicePixelRatio
```

**必须实现并单元测试的换算函数**（`src/features/capture/lib/coords.ts`）：

```ts
export interface MonitorSnapshot {
  id: string;
  /** 物理坐标，该显示器左上角在虚拟桌面中的位置 */
  physicalX: number;
  physicalY: number;
  physicalWidth: number;
  physicalHeight: number;
  /** 该显示器的缩放因子，如 1.0 / 1.25 / 1.5 / 2.0 */
  scaleFactor: number;
  /** 抓到的画面文件路径，尺寸 = physicalWidth × physicalHeight */
  imagePath: string;
}

export function cssToPhysical(monitor: MonitorSnapshot, cssX: number, cssY: number): Point;
export function physicalToCss(monitor: MonitorSnapshot, px: number, py: number): Point;
/** 把一个物理矩形转换到指定显示器的 CSS 坐标，可能返回负值或超出边界（跨屏时） */
export function physicalRectToCss(monitor: MonitorSnapshot, rect: PhysicalRect): CssRect;
```

### 2.3 硬性要求

1. **必须在 Rust 侧声明 Per-Monitor V2 DPI 感知**。Tauri 默认会处理，但要在 `capture_prepare` 里显式确认：
   ```rust
   unsafe { SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2); }
   ```
   否则在 150% 缩放的屏幕上，Win32 返回的窗口矩形会被系统偷偷缩放，导致框选偏移。

2. **窗口矩形必须用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，不要用 `GetWindowRect`**。后者在 Win10+ 上会多返回大约 7px 的不可见阴影边框，导致自动框选框比窗口大一圈。这是所有截图软件都踩过的坑。

3. **每个显示器一个独立的 capture 窗口**，不要创建一个跨越所有显示器的大窗口。跨屏大窗口在混合 DPI 下 WebView 的 `devicePixelRatio` 只有一个值，另一块屏必然错位。

4. **跨屏框选**：用户可以从 A 屏拖到 B 屏。实现方式是各窗口通过 Tauri event `capture-selection-sync` 广播自己的选区（物理坐标），其他窗口收到后把落在自己范围内的那部分画出来。**主控窗口是鼠标按下时所在的那个**，只有它处理鼠标事件并广播。

5. 抓屏的图**不要**经过 base64 传给前端，几千万像素的 base64 会卡死 IPC。显示走原生底图层（§4、01 §2.4），完全不进 WebView。放大镜/取色/马赛克需要的原始像素走自定义 `shot:` 协议异步取，不落盘、不进 IPC，编码用 **24bpp BMP**：PNG 实测更慢也更大（桌面截图的渐变和文字反锯齿让 PNG 压不动，Fast+NoFilter 下 2560×1440 编码 100ms+ 且体积超过 BMP），32bpp BMP 白多传 25% 的无用 alpha。

6. `imagePath` 这个字段名是历史遗留，实际是 `shot:` 协议的 URL 而不是文件路径，也不需要在会话结束时删临时文件——从来没写盘。

## 4. 层结构

底图**不在 WebView 里**。它是一个独立的原生 `WS_EX_LAYERED` 窗口，位于遮罩窗口正下方，由 DWM 合成。理由和实测数据见 01 §2.4，一句话：底图过 Chromium 在 4K 双屏上必然突破 §3.1 的 150ms 预算，且色彩管理转换会破坏 §3.1.2 的像素级一致。

从下到上：

```
[原生窗口] 冻结的屏幕画面，1:1 物理像素，UpdateLayeredWindow 推送，与遮罩原子上屏
[遮罩窗口 WebView，transparent: true]
  <div class="capture-root">
    1. <div id="mask">             压暗遮罩，用 CSS clip-path 挖出选区（不要用 4 个 div 拼）
    2. <canvas id="annotations">   已完成的标注，物理像素分辨率
    3. <canvas id="drafting">      正在绘制中的那一笔，绘制完成后合并到 2
    4. <div id="selection">        选区边框 + 8 个控制点（DOM，不是 canvas）
    5. <div id="size-hint">        尺寸提示
    6. <div id="magnifier">        放大镜（内含一个小 canvas）
    7. <div id="toolbar">          主工具条 + 二级工具条
    8. <div id="text-input">       文字工具的输入框（contenteditable）
  </div>
```

**关键点：**

- **遮罩窗口整体必须没有不透明背景**。`html`/`body`/`.capture-root` 全部 `background: transparent`，压暗只由 `#mask` 自己的半透明色提供。任何一层留了不透明底色，原生底图就被盖住了
- **选区区域是真镂空**：`#mask` 用 `clip-path` 挖洞后，洞里直接看到的是下面那个原生窗口，不是 WebView 画的任何东西。所以选区内的画面天然是像素级原始的，不存在缩放或色彩转换
- **遮罩用 `clip-path` 挖洞**，不要用四个 div 拼四周。`clip-path: polygon(...)` 的 evenodd 规则可以一次性挖出矩形洞，重绘性能好得多：
  ```css
  #mask {
    clip-path: polygon(
      0 0, 100% 0, 100% 100%, 0 100%, 0 0,
      Xpx Ypx, Xpx (Y+H)px, (X+W)px (Y+H)px, (X+W)px Ypx, Xpx Ypx
    );
  }
  ```
- **放大镜、取色、马赛克需要的原始像素是异步到的**。底图像素通过 `shot:` 协议流进 WebView，在画面可见之后 150-250ms 才可用（实测 230-330ms 到位）。这三个工具在像素到位前**不渲染**，不要在这期间画一个空的或拉伸的放大镜。像素存成 `ImageBitmap` 放 ref，不进 React state
- **canvas 必须是物理像素分辨率**：`canvas.width = cssWidth * dpr`，然后 `ctx.scale(dpr, dpr)`。否则标注在高 DPI 屏上是糊的
- **拖拽时不要 setState 触发 React 重渲染**。用 `useRef` + 直接操作 DOM style / canvas，在 `requestAnimationFrame` 里更新。React state 只在拖拽结束时更新一次。这是达到 60fps 的必要条件

## 5. 标注工具实现

### 5.1 数据模型

```ts
type Annotation =
  | { kind: 'rect';    id: string; rect: Rect; color: string; lineWidth: number; filled: boolean }
  | { kind: 'ellipse'; id: string; rect: Rect; color: string; lineWidth: number; filled: boolean }
  | { kind: 'arrow';   id: string; from: Point; to: Point; color: string; lineWidth: number; style: 'thin' | 'thick' }
  | { kind: 'pen';     id: string; points: Point[]; color: string; lineWidth: number }
  | { kind: 'mosaic';  id: string; points: Point[]; brushSize: number; mode: 'pixelate' | 'blur' }
  | { kind: 'text';    id: string; at: Point; content: string; color: string; fontSize: number; bold: boolean };
```

- 用一个 `annotations: Annotation[]` 数组 + `undoStack` 管理
- Ctrl+Z 弹出最后一个；**第一版不做重做**（微信也没有）
- 所有坐标存**选区内的相对物理坐标**，这样移动选区时标注跟着走

### 5.2 各工具要点

**矩形 / 椭圆**
- 按下起点，拖拽到终点。按住 Shift 约束为正方形 / 正圆
- 空心模式：`strokeRect`。实心模式：`fillRect` + 60% 不透明度

**箭头**
- 不要用简单的直线 + 两条斜线。微信的箭头是**实心三角形 + 渐宽的尾巴**，看起来更精致
- 实现：以起点到终点为轴，箭头尾部宽 = lineWidth，头部三角形底边宽 = lineWidth × 4，三角形长度 = lineWidth × 6。用 `Path2D` 一次性描出闭合路径填充
- 按住 Shift 约束到 15° 的整数倍

**画笔**
- 采集 pointermove 的点序列。**必须做平滑**，否则线条是折线不是曲线
- 平滑算法：二次贝塞尔，每两个采样点之间用它们的中点作为端点，原采样点作为控制点：
  ```
  ctx.moveTo(p0);
  for i in 1..n-1:
      mid = (p[i] + p[i+1]) / 2
      ctx.quadraticCurveTo(p[i], mid)
  ```
- `lineCap = 'round'`, `lineJoin = 'round'`

**马赛克**
- 两种模式，默认 pixelate
- pixelate 实现：以 brushSize 为格子大小，把画笔经过区域内的原图像素按格子取平均色填充。**从背景 canvas 取原始像素**，不要从已叠加标注的画布取
- blur 实现：对经过区域做半径 = brushSize/2 的box blur（跑 3 遍近似高斯）
- 性能：不要每次 pointermove 都全量重算。维护一个 `Set<gridKey>` 记录哪些格子被涂过，只处理新增的格子
- 马赛克是**破坏性**的，撤销时需要重新从背景重绘整个标注层

**文字**
- 点击位置出现一个 `contenteditable` 的 div，光标闪烁，可直接打字
- 支持多行（Enter 换行），Esc 或点击别处提交
- 提交后转成 canvas 上的文字绘制。多行用 `fillText` 逐行画，行高 = fontSize × 1.4
- 输入框的字体、字号、颜色要和最终绘制**完全一致**，做到所见即所得
- 文字有 1px 的深色描边（`strokeText` 用 `rgba(0,0,0,0.3)`），保证在浅色背景上也看得清
- 已提交的文字**可以点击重新编辑**（点击文字包围盒时进入编辑）

## 6. 贴图（Pin）

微信没有这个功能，参照 Snipaste 的行为。

### 6.1 创建

- 编辑态下按 `Ctrl+P` 或点工具条的 📌
- 立即在原选区的**屏幕位置**创建一个贴图窗口，尺寸 = 选区尺寸
- 有一个 180ms 的出现动画：`scale(0.96) → scale(1)` + 轻微阴影加深，缓动 `cubic-bezier(0.32, 0.72, 0, 1)`
- 截图遮罩同时关闭

### 6.2 贴图窗口行为

| 操作 | 行为 |
|---|---|
| 左键拖拽 | 移动窗口 |
| 滚轮 | 缩放，每格 ±10%，范围 20%–500%。以鼠标位置为锚点 |
| Ctrl + 滚轮 | 调整不透明度，每格 ±10%，范围 20%–100% |
| 双击 | 隐藏/显示（隐藏时只留一个 24×24 的小圆点在原位） |
| 右键 | 上下文菜单 |
| Esc / 中键 | 关闭（有 120ms 缩小淡出动画） |
| 拖到屏幕边缘 | 吸附对齐 |

**右键菜单项**：复制图片 · 另存为 · 识别文字 · 翻译 · 恢复原始大小 · 100% 不透明度 · 置顶(开关) · 关闭 · 关闭全部贴图

### 6.3 实现要点

- 贴图窗口 `transparent: true` + `decorations: false` + `always_on_top: true` + `skip_taskbar: true`
- 窗口有 8px 的透明外边距用于绘制阴影（`box-shadow: 0 8px 32px rgba(0,0,0,0.24)`），所以窗口实际尺寸 = 图片尺寸 + 16px
- 拖动用 `getCurrentWindow().startDragging()`，不要自己算坐标
- 缩放时窗口尺寸和内部 `<img>` 同步改，`image-rendering: auto`（缩小时平滑，放大到 200% 以上切 `pixelated`）
- **贴图窗口在系统重启后不恢复**，但设置里可开"退出时记住贴图"

## 7. 已知难点与处理方案

| 难点 | 方案 |
|---|---|
| 遮罩窗口出现前，屏幕上短暂闪一下 | 窗口在**启动时**就建好并隐藏（WebView2 首次加载 400ms+，放热键路径上必爆预算）。热键时前端发 `capture_overlay_ready`，Rust 收到再上屏 |
| 底图先亮一帧未压暗的原图 | 底图和遮罩是两个 HWND，必须用 `BeginDeferWindowPos`/`DeferWindowPos`/`EndDeferWindowPos` 同批提交。见 01 §2.4 |
| 抓屏耗时（4K 双屏约 60–120ms） | 在 Rust 侧并行抓取各显示器（`rayon` 或 tokio task）。实测 3840×2160 单屏热抓 **49ms**（xcap + WGC）。若双 4K 超预算，再上 DXGI Desktop Duplication 常驻 warm session |
| **首次** F1 比后续慢 90ms | 首次抓屏要建 D3D 设备、开 WGC 会话：冷 137ms vs 热 49ms，首次 hotkey→可见 163ms。**解法**：启动后在后台线程空跑一次抓屏（`ScreenCapture::warm_up`），把这笔开销挪到启动期。之后首次 79ms、后续 67–72ms |
| 热身状态**会失效**，137ms 悄悄回来 | GPU 侧状态不是永久的：插拔屏 / 改分辨率 / 改缩放（`WM_DISPLAYCHANGE`）、睡眠唤醒（`WM_POWERBROADCAST` + `PBT_APMRESUME*`）、显卡驱动 TDR 之后都可能没了，而症状是沉默的 —— 用户偶然遇到一次慢 F1，日志里只有 `capture_ms` 变大。**解法**：这些时机各重新热身一次（`capture::warmup`）。TDR 没有窗口消息、也拿不到 xcap 内部的 D3D 设备，所以只能间接覆盖（驱动重置几乎总跟一个 `WM_DISPLAYCHANGE`）；真漏掉时代价上限是一次慢抓屏，且那次抓屏本身就把状态热回来了，所以只打一条 warn 暴露出来，不做事后补救 |
| 窗口枚举耗时 | 枚举顶层窗口很快（<5ms）。子控件枚举**懒执行**：鼠标停在某窗口上超过 80ms 才枚举它的子控件，并缓存 |
| 全屏独占的游戏/视频上截图黑屏 | xcap 用的是 DXGI Desktop Duplication，一般没问题。若遇到，降级到 GDI `BitBlt`。检测方式：抓到的图全黑则重试一次 GDI |
| 用户在截图时切换了输入法 | 截图窗口获得焦点时禁用 IME（除非在文字工具的输入框里） |
| 高刷屏（144Hz+）拖拽掉帧 | 严格遵守第 4 节的"拖拽不 setState"原则；用 `will-change: clip-path` 提示合成器 |
