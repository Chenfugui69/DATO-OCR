**关于 `react-screenshots`：** 它是现成的微信式截图 UI（MIT）。评估两条路：

- **路线 A（推荐）**：fork 到 `src/features/capture/vendor/`，在其基础上改造。它的选区拖拽、8 点调整、工具条定位逻辑已经打磨过，省 1–2 周。但它的视觉是微信风不是苹果风，样式需全部重写；它也不含窗口自动检测、放大镜、贴图，这些要自己加。
- **路线 B**：完全自己写。可控性最高，但要重新踩一遍多显示器、DPI、边界吸附的坑。

**决定：走路线 A**，第一版先 fork 改造快速跑通，M6 阶段再评估是否需要重写。fork 时必须保留其 MIT 许可声明。

## 2. 窗口定义

DATO OCR 是多窗口应用。所有窗口在 `tauri.conf.json` 中**只声明主窗口**，其余全部运行时创建（截图窗口数量取决于显示器数量，贴图窗口数量不定）。

其中截图遮罩虽然是运行时创建，但**必须在启动时就建好并隐藏**，热键路径上只允许 `show`：WebView2 首次创建加载 HTML 要 400ms 以上，放在热键之后 150ms 预算直接爆掉。这条同样适用于剪贴板面板（见 05 §常驻隐藏）。

| 标识 | 用途 | 创建时机 | 关键属性 |
|---|---|---|---|
| `main` | 主窗口（侧边栏 + 内容区） | 启动时创建但隐藏 | 1120×720，最小 880×560，无系统标题栏（自绘），可调整大小，透明背景 + Mica |
| `capture-{monitor_id}` | 截图遮罩（**只画压暗和选区**），每个显示器一个 | **启动时创建但隐藏**，热键时只 show | 覆盖该显示器物理区域，无边框，置顶，跳过任务栏，透明，不可调整大小，`focus: true` 仅主显示器 |
| （无标签，非 Tauri 窗口）| 截图底图，每个显示器一个 | 启动时创建但隐藏 | 原生 `WS_POPUP` + `WS_EX_LAYERED`/`TRANSPARENT`/`NOACTIVATE`/`TOOLWINDOW`，内容用 `UpdateLayeredWindow` 推送，z 序紧贴对应遮罩之下 |
| `pinned-{uuid}` | 贴图窗口 | 用户点贴图 | 尺寸=图片尺寸，无边框，置顶，跳过任务栏，透明，可拖动 |
| `clipboard` | 剪贴板面板 | 启动时创建但隐藏 | 底部横向：全屏宽 × 320 高，吸附屏幕底部；竖版：380×620，跟随鼠标。无边框，置顶，跳过任务栏，透明 |
| `ocr-result` | 识字结果窗口 | OCR 完成后 | 900×620，无系统标题栏，可调整大小 |

### 2.2 关于 `transparent` 的重大坑

**主窗口不要设 `transparent: true`。**

Windows 上一旦设了 `transparent: true`，窗口会失去系统边框，导致：
- 无法调整大小（已知 Electron/Tauri 共有问题）
- Mica / Acrylic 效果失效

**正确做法**：`transparent: false` + `backgroundColor: "#00000000"` + `decorations: false`，然后调用 `window-vibrancy` 的 `apply_mica()` / `apply_acrylic()`。CSS 里 `html` 和 `body` **都要**设 `background: transparent`（只设一个不生效）。

截图遮罩窗口和贴图窗口则**必须** `transparent: true`，因为它们要真正镂空。

### 2.3 窗口特效降级链

启动时按顺序探测，用第一个可用的：

```
Windows 11 22H2+  →  apply_mica(dark)        主窗口
                  →  apply_acrylic()          剪贴板面板、OCR 窗口
Windows 11 早期    →  apply_acrylic()
Windows 10 1803+  →  apply_acrylic()（有拖动卡顿，仅用于不常拖动的窗口）
其他 / 透明度关闭  →  不加特效，用不透明纯色底
```

探测逻辑放在 `src-tauri/src/platform/windows/vibrancy.rs`，结果缓存到 `AppState`，并通过 `get_visual_capabilities` command 暴露给前端，前端据此决定内层玻璃的强度。

### 2.4 截图底图为什么是原生窗口而不是 WebView 里的 `<canvas>`

M0 实测（**3840×2160 @ 150% 缩放单屏**，24bpp BMP 24.9MB）：把冻结底图送进 WebView 显示，传输+解码 170ms，全链路 244ms。这个代价随像素数线性涨，双 4K 就是翻倍，02 §3.1 的 150ms 预算必然爆掉。此外底图过 Chromium 会经色彩管理转换，广色域屏上会破坏 02 §3.1.2 要求的"像素级一致"。

所以底图走原生层：每个显示器一个 `WS_EX_LAYERED` 窗口，`CreateDIBSection` 拿 32bpp BGRA 缓冲，`UpdateLayeredWindow` 直接交给 DWM，不经 Chromium。同一台机器上热键到可见降到 **70ms**（首次 80ms）。

**两个层必须原子上屏**：用 `BeginDeferWindowPos` / `DeferWindowPos` / `EndDeferWindowPos` 把底图窗口和遮罩窗口放在同一批提交，否则会先亮一帧未压暗的底图。底图窗口置于对应遮罩之下（`hWndInsertAfter` 传遮罩 HWND），遮罩自己进 `HWND_TOPMOST`。

**像素数据仍然要进 WebView**，但挪出关键路径：放大镜（6 倍实时取色）、取色快捷键、马赛克工具都要原始像素，按需 IPC 在 74ms 往返下撑不住 60fps。做法是画面 70ms 先出，像素通过 `shot:` 协议异步流入，230-330ms 到位，放大镜在此之前不渲染。用户从看见画面到手开始动至少 200-400ms，感知不到。

两类窗口都要 `WDA_EXCLUDEFROMCAPTURE`，否则连续截图会抓到自己。诊断期可用环境变量 `CHENOCR_ALLOW_SELF_CAPTURE=1` 临时关掉，这是脚本化视觉验证的唯一手段——否则截出来的图里遮罩是空的。

底图层的所有 GDI 操作**必须在 UI 线程**：`HWND`/`HDC`/`HBITMAP` 存在 `thread_local` 里，非 UI 线程的调用要用 `run_on_main_thread` 投递。

### 3.2 Event 清单

#### M0 截图链路（Rust 驱动）

`capture-hotkey` 仍会广播给主窗口，用于需要联动的 UI；但它不再触发抓屏，也不再由
主窗口负责打开遮罩。实际链路是：

1. 全局热键回调直接进入 Rust `capture::start`，抓取所有显示器并创建会话。
2. Rust 将冻结画面装入原生 `BackdropLayer`，摆好启动时预建的各个遮罩窗口，并向对应
   遮罩发送 `capture-session-start`。
3. 遮罩前端调用 `capture_prepare` 读取会话元信息；压暗层挂载后调用
   `capture_overlay_ready`，Rust 用 `DeferWindowPos` 将底图和遮罩原子显示。
4. 底图原始像素随后通过 `shot:` 协议异步进入 WebView；解码完成后调用
   `capture_overlay_pixels_ready`，这条路径不在“热键到可见”的关键预算内。

这条链路替代旧版“热键 → `capture-hotkey` → 主窗口 → `capture_prepare` → 打开遮罩”
的描述，保留事件只是为了兼容主窗口联动和现有事件契约。

Rust → 前端推送：

| 事件名 | 载荷 | 说明 |
|---|---|---|
| `clipboard-changed` | `ClipItem` | 检测到新的剪贴板内容 |
| `capture-hotkey` | `{ mode: 'normal' \| 'longshot' \| 'ocr' }` | 热键触发通知；Rust 已直接驱动截图，主窗口仅按需联动 |
| `capture-session-start` | `{ sessionId, monitor }` | Rust 发给对应的常驻遮罩，开始读取本次会话元信息和底图像素 |
| `longshot-frame` | `{ sessionId, frameIndex, previewBase64, matched }` | 长截图新帧已拼接 |
| `ocr-progress` | `{ stage, percent }` | 长文本 OCR 进度 |
| `engine-download-progress` | `{ engine, received, total }` | 引擎下载进度 |
| `visual-capabilities-changed` | `VisualCapabilities` | 系统主题 / 透明度 / 电源状态变化 |
| `settings-changed` | `Settings` | 设置在其他窗口被修改，各窗口同步 |
| `tray-action` | `{ action }` | 托盘菜单点击 |

## 4. 状态管理约定

### 4.1 Rust 侧

```rust
pub struct AppState {
    pub db: Pool<SqliteConnectionManager>,
    pub settings: RwLock<Settings>,
    pub visual: RwLock<VisualCapabilities>,
    pub capture_session: Mutex<Option<CaptureSession>>,
    pub longshot_sessions: Mutex<HashMap<String, LongshotSession>>,
    pub ocr: OcrManager,           // 内部管理 sidecar 进程生命周期
    pub pinned_windows: Mutex<HashMap<String, PinnedMeta>>,
}
```

用 `parking_lot` 的锁，不用 std 的。**禁止在持锁状态下 await。**

### 4.2 前端

- **服务端状态**（数据库里的数据）走 TanStack Query，不要放进 Zustand
- **UI 状态**（当前选中项、面板开关、截图工具选择）走 Zustand
- **设置**单独一个 Zustand store，启动时从 Rust 拉一次，监听 `settings-changed` 同步
- 每个窗口是独立的 WebView，各自有独立的 store 实例。跨窗口通信一律走 Tauri event，不要试图共享内存

```ts
      main: resolve(__dirname, 'index.html'),
      capture: resolve(__dirname, 'capture.html'),
      pinned: resolve(__dirname, 'pinned.html'),
      clipboard: resolve(__dirname, 'clipboard.html'),
      ocrResult: resolve(__dirname, 'ocr-result.html'),
    }
  }
}
```

### 5.2 体积控制清单

打包后如果超过 40 MB，按这个顺序砍：

1. 确认 `[profile.release]` 的 `opt-level = "s"`、`lto = true`、`strip = true` 都生效
2. MiSans 字体做子集化 —— 只保留 GB2312 常用字 + 拉丁字母 + 常用标点，可以从 10 MB 压到 2–3 MB。用 `fonttools pyftsubset`
3. RapidOCR 只保留中英文模型，删掉其他语种的 `*_rec_infer` 目录（每组约 10 MB）
4. NSIS 用 LZMA 压缩
5. 检查是否误打包了 source map、开发依赖
6. 用 `cargo bloat --release --crates` 找出体积大户

### 5.3 签名与更新

- Windows 代码签名证书需要单独采购（EV 证书约 2000–4000 元/年）。**第一版可以不签名**，但用户首次运行会看到 SmartScreen 警告，需要在下载页说明
- 自动更新用 `tauri-plugin-updater`，需要生成一对签名密钥（`pnpm tauri signer generate`），私钥**绝不入库**
- 更新服务器第一版可用 GitHub Releases 的静态 JSON（即使代码闭源，Release 页可以公开）

## 6. 测试策略

第一版不追求高覆盖率，重点保三类：

| 类型 | 工具 | 覆盖什么 |
|---|---|---|
| Rust 单元测试 | `cargo test` | 长截图拼接算法、OCR 段落重组、剪贴板去重哈希、DPI 坐标换算 |
| 前端单元测试 | Vitest | 选区几何计算、边界吸附、工具条定位算法 |
| 人工回归 | 检查清单 | `08-开发排期与验收.md` 里每个阶段的验收项 |

**坐标换算和拼接算法必须有单元测试**，这两处出 bug 最隐蔽、最难人工发现。
