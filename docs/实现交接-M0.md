## 1. 当前状态

### 1.1 M0 验收清单（规格 08）

| # | 验收项 | 状态 | 依据 |
|---|---|---|---|
| 1 | 安装包 < 15 MB | **通过** | NSIS 1.83 MB / exe 5.52 MB |
| 2 | F1 到遮罩可见 < 200ms | **通过** | 首次 79ms、后续 67–73ms（仅单屏，见 §6） |
| 3 | 遮罩背景与真实桌面像素级一致 | **通过** | `verify-backdrop.ps1` 连跑 4 次，494656 像素 0 差异 |
| 4 | 主屏 150% + 副屏 100% 双屏背景正确 | **阻塞** | 只有一块屏 |
| 5 | 副屏在主屏左侧（负坐标）正确 | **阻塞** | 只有一块屏 |
| 6 | 拖拽框选流畅、肉眼无卡顿 | **待人工确认** | 脚本量不了手感 |
| 7 | Enter 粘贴出的图尺寸精确 | **通过** | `verify-clipboard.ps1`：400×300 精确，alpha=255 |
| 8 | Esc 干净退出，无残留窗口/进程 | **通过** | 同上脚本尾部检查 |

M0 退出前另有两条补债（写在规格 08）：Clippy **已补**，ESLint **未补**。

### 1.2 阻塞项及解除条件

| 阻塞项 | 解除条件 |
|---|---|
| 验收 4、5 | 第二块显示器到货（用户走 HDMI 诱骗器，不装驱动） |
| 双屏延迟复测 | 同上。**这是硬件到货后的第一件事**，优先于任何 M1 功能 |

关于虚拟显示器：用户明确说过，虚拟屏在 DXGI Desktop Duplication 下偶有怪癖，
**虚拟屏上发现的抓屏异常必须在真实屏上复现后才算数**。所以别用 Parsec VDD 之类的
方案代替真实第二块屏来"完成"验收 4、5。

### 1.3 待人工确认项

验收 6 之外，整个"观感"维度都没有人眼验过。用户列的检查点：

- 按 F1 有没有闪一帧（未压暗的原图、或者空白）
- 拖拽跟不跟手
- 遮罩边缘移动时抖不抖
- 底图和真实桌面之间有没有位移或色差
- Esc 退不退干净

用户的判断是："M0 的数值那一半答完了，'Tauri 做的遮罩用起来像不像原生工具'
这一半没人验过，且只有人能验。这是重新考虑选型成本最低的最后一刻。"

**接手方不要跳过这一步直接进 M1。**

### 2.2 尚未回写进规格的实现细节

这些在代码注释里写清了，但规格文档还没吸收。接手方如果要改动对应部分，**先看代码
注释**，别只看规格：

1. **`ScreenCapture` trait 多了 `warm_up`**，规格 07 §2 的 trait 列表里没有。
   热身失效重来的整套策略（`capture::warmup` + `platform::on_capture_state_lost`）
   规格里完全没有对应条目。
2. **`BackdropLayer` 是规格 07 那七个 trait 之外新加的第八个**。`platform/mod.rs`
   的文档表格里标了"规格外新增"，但规格 07 本身没更新。
3. **`WindowEffects::native_handle`** 是为了把遮罩 HWND 交给 `show_above` 排 z 序
   而加的，规格 07 §2 没有这个方法。
4. **整条截图链路由 Rust 驱动**，不走规格 01 §3.2 描述的"热键 → 事件 → 主窗口调
   `capture_prepare` → 打开遮罩"。理由见 `capture/mod.rs` 文件头。对前端而言
   `capture_prepare` 的返回结构与规格一致，只是不再由它触发抓屏。
5. **`capture_overlay_ready` / `capture_overlay_pixels_ready` / `capture_overlay_boot`**
   这几个 command 规格 01 §3.1 的清单里没有，是两阶段上屏拆出来的。

### 2.3 规格里被发现不可行或需调整的条目

| 规格条目 | 问题 | 现状 |
|---|---|---|
| `02` §2.3 原第 5 条：抓屏图写 PNG 到临时目录 | 桌面截图 PNG 压不动（壁纸/文字反锯齿），Fast+NoFilter 下编码 100ms+ 且**体积比 BMP 还大**；落盘 + `convertFileSrc` 更慢 | 已改（见 §2.1） |

## 3. 看起来多余但不能删的东西

**这一节是本文件的核心。** 每条都是"我实现时想删或想简化、但忍住了"的。
格式统一：是什么 / 为什么留 / 删掉会怎样 / 什么条件下可以删。

### 3.1 `backdrop.rs` 创建窗口时的 `WS_EX_TOPMOST`

- **是什么**：`platform/windows/backdrop.rs` 里 `CreateWindowExW` 的扩展样式含
  `WS_EX_TOPMOST`。
- **为什么留**：z 序分两个波段，topmost 的一律在非 topmost 之上。底图必须和遮罩
  同波段，否则系统里任何常驻置顶窗口（音量 OSD、画中画、Teams 悬浮条、PowerToys
  置顶窗、录屏工具条、输入法候选窗、任务管理器"置于顶层"）会卡在"遮罩之下、底图
  之上"的夹层里，透过真镂空的选区**活着浮在冻结画面上**。
- **它当前确实是冗余的**：实测（`probe-zorder.ps1`，`CHENOCR_BACKDROP_NO_TOPMOST=1`
  可复现）不加这个样式，运行时读回的 `GWL_EXSTYLE` 仍是 `0x080800A8`，含
  `WS_EX_TOPMOST` —— 因为 `DeferWindowPos(hWndInsertAfter = 遮罩)` 把它插到了一个
  topmost 窗口之后，`SetWindowPos` 文档说这会让被摆的窗口自己也变 topmost。
- **删掉会怎样**：现在删掉不会立刻出问题。但波段归属就从"窗口样式声明的硬事实"
  退化成"插入锚点恰好是个 topmost 窗口"的副作用。哪天 `show_above` 改成用
  `HWND_TOP` 或别的锚点，就变成**间歇缺陷：只在截图时屏幕上恰好有置顶窗口才出现**，
  单跑验收脚本大概率是过的，极难查。
- **什么条件下可以删**：让底图成为遮罩的 owner（对顶层窗口设 `GWLP_HWNDPARENT`），
  OS 保证 owned 窗口恒在 owner 之上，那时波段和顺序都不再依赖调用约定。但改
  Tauri/WebView2 窗口的 owner 有没有副作用**尚未验证**，没验之前不要动。
- **注意它替代不了显式插入**：同一波段内的先后仍由 `DeferWindowPos` 决定。

### 3.2 `verify-backdrop.ps1` 里的三道防护

这个脚本验"底图是冻结的、且没有窗口能从选区里浮出来"。三道防护各挡一种**假结论**，
删任何一道，脚本都会变成"看着在跑、其实什么都没验"。

**(a) 对照组：先证明入侵窗口本来抓得到**

- **为什么留**："B 里没有洋红"有两种解释：底图挡住了（产品对），或者那个窗口压根
  没画出来（测试废了）。对照组先在无遮罩状态抓一次，确认能抓到 1947 个洋红采样点。
- **删掉会怎样**：WinForms 窗口只要没泵消息、或位置算错、或被别的东西盖住，测试就
  **假通过**。假通过比失败危险得多。
- **可以删的条件**：没有。

**(b) 入侵者必须是 topmost，而且必须在按 F1 之前就存在**

- **为什么留**：用**普通窗口**当入侵者，它永远在非 topmost 波段，压根到不了遮罩
  下方那个夹层 —— 不管产品对错都会**假通过**。这是我第一版真的踩到的，还基于错误
  结论改了产品代码。
- **删掉/改错会怎样**：见上，测试退化成永远绿灯。
- **可以删的条件**：没有。

**(c) 冻结之后只挪位置、不动 z 序（`SWP_NOZORDER`）**

- **为什么留**：冻结后才把入侵窗口设成 `HWND_TOPMOST`，会把它插到 topmost 波段
  **最顶上**，连遮罩一起盖住 —— 不管产品对错都会**假失败**。任何截图工具都拦不住
  一个被摆在自己之上的窗口，测它等于测操作系统。
- **删掉会怎样**：测试永远红灯，而且会诱导接手方去"修"一个不存在的缺陷。
- **可以删的条件**：没有。

**(d) 取基准（A）和按 F1 之间不许有任何屏幕变化，输出全部攒到比对结束后再打**

- **为什么留**：比对区往往压在终端窗口上。一句 `Write-Host` 就会滚动终端，于是
  冻结下来的是变化**之后**的画面，和 A 天然不同。
- **删掉会怎样**：脚本时过时不过。这条真的发生过：我一度以为是 z 序 bug，基于错误
  假设改了产品代码，白查半天。
- **可以删的条件**：没有。脚本里那个 1200ms 静默沉降期同理。

### 3.3 启动时的丢弃式抓屏热身

- **是什么**：`capture::warmup::install()` → `ScreenCapture::warm_up()`，在后台线程
  空跑一次抓屏，结果直接丢掉。
- **为什么留**：首次抓屏要建 D3D 设备、开 WGC 会话，实测 137ms vs 热态 49ms。
  这 90ms 刚好让第一次 F1 从 79ms 冲到 163ms，突破规格 00 §6.4 的 150ms 预算。
- **删掉会怎样**：**用户按下的第一次 F1 超预算**，而后续都正常 —— 于是很容易被当成
  "偶发"忽略掉。这是最典型的"删了跑测试还是绿的"陷阱：`measure-m0.ps1` 连按三轮，
  只有第一轮会露出问题。
- **可以删的条件**：改用 DXGI Desktop Duplication 常驻 warm session，那时热身状态
  由常驻会话自己维持。M0 期间评估过，单屏用不上所以没做。

### 3.4 热身失效后重新热身的整套机制

- **是什么**：`platform/windows/system_events.rs` 一个隐藏顶层窗口 + `capture::warmup`
  里的去抖调度。
- **为什么留**：GPU 侧热身状态不是永久的。插拔屏 / 改分辨率 / 改缩放
  （`WM_DISPLAYCHANGE`）、睡眠唤醒（`WM_POWERBROADCAST` + `PBT_APMRESUME*`）之后
  可能已经没了，137ms 会悄悄回来。
- **删掉会怎样**：症状极其隐蔽 —— 用户合盖再打开，之后第一次 F1 慢，日志里除了
  `capture_ms` 变大没有任何线索。
- **可以删的条件**：同 3.3。

**这里面有三个各自的"不能删"细节：**

- **监听窗口必须是真正的顶层窗口，不能用 `HWND_MESSAGE`。** message-only 窗口
  **收不到广播消息**，而这两个消息正是广播给顶层窗口的。用了 `HWND_MESSAGE` 的话
  代码看着完全正常、编译通过、永远不触发。`verify-rewarm.ps1` 专门断言
  `GetParent == 0`。
- **`compare_exchange` 去抖不是过度设计。** 插拔一次屏可能连发好几个
  `WM_DISPLAYCHANGE`，每个都热身一次就是连着好几个 137ms。
- **热身必须丢到后台线程。** 窗口过程跑在 UI 线程上，在那儿同步跑 137ms 会卡界面。

### 3.5 `note_capture_cost` 那条只打日志、不做补救的 warn

- **是什么**：抓屏耗时超过 `100ms × 屏数` 时打一条 warn。
- **为什么留**：显卡驱动 TDR **没有窗口消息**，正规检测要自己持有 D3D 设备去查
  `GetDeviceRemovedReason`，但设备在 xcap 内部，我们碰不到。所以 3.4 那套机制覆盖
  不到纯 TDR（只能靠"驱动重置几乎总跟一个 `WM_DISPLAYCHANGE`"间接覆盖）。这条日志
  是那个残留缺口的**唯一**可观测性。
- **为什么不做补救**：那次慢抓屏本身已经把状态热回来了，事后再热身没有意义。真漏掉
  的代价上限就是一次慢 F1。
- **删掉会怎样**：TDR 导致的性能退化变成完全沉默的。
- **可以删的条件**：改成自己持有 D3D 设备（比如上 DXGI duplication），那时能真正
  检测设备丢失。

### 3.6 `CaptureOverlay.tsx` 里失败路径上的 `captureCancel()`

- **是什么**：前端 `capture-session-start` 处理失败时，除了报错还要调
  `captureCancel()`。
- **为什么留**：会话存在 Rust 侧。前端抛异常但不收会话，会话就一直挂着，之后**每次
  F1 都被"已在截图中"挡回去**。而遮罩窗口是隐藏的，用户看到的是热键彻底失灵、
  连报错都看不见。
- **删掉会怎样**：见上。一次前端异常等于截图功能永久失效到重启。
- **可以删的条件**：Rust 侧给会话加超时自动回收。
- **踩过**：是。CSP 拦 fetch 那次就是这个症状（§5.1）。

### 3.7 `reportError` 通道，以及"只报不炸"的像素加载失败处理

- **是什么**：`src/lib/ipc.ts` 的 `reportError` + `commands::system::report_error`。
- **为什么留**：遮罩窗口既隐藏又没有 devtools，是全项目最深的调试盲区。里面抛出的
  异常在界面上完全不可见，表现只是"按 F1 没反应"。
- **删掉会怎样**：只能靠改代码二分查找。
- **另外**：像素加载（`shot:` 协议那条异步路径）失败时是**只报不炸**的 —— 画面已经
  在屏幕上了，框选和复制都不依赖那些像素，受影响的只有放大镜和取色，属于降级不是
  失败。别把它改成 `setFailure`。

### 3.8 `self_capture.rs` 与 `CHENOCR_ALLOW_SELF_CAPTURE`

- **是什么**：一个环境变量，开了就不给自己的窗口设 `WDA_EXCLUDEFROMCAPTURE`。
- **为什么留**：正常必须排除自己，否则连续截图会抓到上一次的遮罩。但**排除之后，
  任何脚本化的视觉验证都截不到遮罩**（截出来是空的）。这个开关是
  `verify-backdrop.ps1` / `shoot-overlay.ps1` 能工作的前提。
- **删掉会怎样**：所有视觉验收脚本失效，只能靠人眼。
- **可以删的条件**：没有。这是测试基础设施。

### 3.9 `CHENOCR_BACKDROP_NO_TOPMOST`

- **是什么**：诊断开关，创建底图窗口时不加 `WS_EX_TOPMOST`。
- **为什么留**：3.1 那个结论（"波段归属靠插入锚点带进来的"）只有靠它才能复现验证。
  没有它，3.1 就退化成一段无法检验的断言。
- **可以删的条件**：3.1 本身被 owner 方案取代时，一起删。

### 3.10 `platform/` 那四条铁律和 `native_handle` 的 `u64` 包装

- **是什么**：`WindowEffects::native_handle` 返回 `u64` 而不是 `HWND`。
- **为什么留**：规格 07 §1 第 4 条铁律 —— 平台句柄不能出现在 `platform/` 之外的
  签名里。包成 `u64` 看着别扭，但这是 macOS 移植不至于推翻接口的前提。
- **删掉会怎样**：`HWND` 泄进共享代码，macOS 移植时这些签名全要改。

### 3.11 `capture/backdrop.rs` 的格式开关（`CHENOCR_BACKDROP_FORMAT`）

- **是什么**：BMP / PNG 二选一的运行时开关。
- **为什么留**：PNG 结论（比 BMP 又慢又大）是实测出来的，反直觉。留着开关让后人能
  自己复测而不是相信注释。
- **可以删的条件**：确认不会再有人提"要不要换 PNG"的时候。优先级很低，留着几乎零
  成本。

### 3.12 所有 PowerShell 脚本的 UTF-8 BOM

- **为什么留**：没有 BOM，PowerShell 按 ANSI 解释中文注释，中文字节里的 `0x5C` 等
  会破坏词法分析，报出 `MissingEndCurlyBrace` 这种**跟真实原因毫无关系**的语法错。
- **删掉会怎样**：脚本报无法理解的语法错。本次交接前刚踩过一次（`verify-rewarm.ps1`）。
- **可以删的条件**：全项目放弃 PowerShell 5.1 兼容。

### 3.13 底图层所有 GDI 操作绑 UI 线程（`thread_local` + `check_thread`）

- **为什么留**：Windows 上窗口归创建它的线程所有，`HWND`/`HDC`/`HBITMAP` 跨线程用
  是未定义行为。截图是在新线程上跑的（`trigger_capture`），所以必须显式
  `run_on_main_thread` 投递回去（`capture::with_ui_thread`）。
- **删掉会怎样**：偶发的绘制失败或崩溃，且难复现。
- **可以删的条件**：没有。

## 4. 调试设施

### 4.1 遮罩窗口的前端异常从哪看

遮罩窗口**隐藏 + 无 devtools**，是全项目最深的盲区。三条路：

1. **`reportError` 通道**（首选）。前端 `import { reportError } from '@/lib/ipc'`，
   调 `reportError('scope', message)`，会写进 Rust 日志，级别 ERROR，带 `scope` 字段。
   凡是"用户只会感觉到功能没反应"的失败路径都该往这里报一份。
2. **日志文件**：`%APPDATA%\CHENOCR\logs\`，按天滚动。
3. **提高日志级别**：`$env:CHENOCR_LOG = 'chenocr_lib=debug,chenocr=debug,warn'`。
   语法是 `tracing_subscriber` 的 `EnvFilter`。

### 4.2 环境变量开关

| 变量 | 值 | 作用 |
|---|---|---|
| `CHENOCR_LOG` | `EnvFilter` 语法 | 日志级别。默认见 `logging.rs` |
| `CHENOCR_ALLOW_SELF_CAPTURE` | `1` / `true` | 不排除自己的窗口，**视觉验证脚本必须开**（§3.8） |
| `CHENOCR_BACKDROP_NO_TOPMOST` | 任意非空 | 底图窗口不加 `WS_EX_TOPMOST`，验 §3.1 |
| `CHENOCR_BACKDROP_FORMAT` | `bmp` / `png` | 底图像素编码格式，默认 bmp |

PowerShell 里设：`$env:CHENOCR_ALLOW_SELF_CAPTURE = '1'`，
清：`Remove-Item Env:\CHENOCR_ALLOW_SELF_CAPTURE`。
`scripts/lib.ps1` 的 `Set-ChenocrEnv` 会显式设置这几个，避免上一次运行的残留污染
下一次（踩过）。

### 4.3 脚本

全在 `scripts/`，都不属于产品代码。都需要先 `corepack pnpm tauri build --no-bundle`
（**不能**用裸 `cargo build`，那样出来的包指向 Vite 开发服务器，遮罩页面加载不出来）。

| 脚本 | 用途 |
|---|---|
| `measure-m0.ps1 <exe> [bmp\|png]` | 连按三轮 F1，打印分段耗时 |
| `verify-backdrop.ps1 <exe>` | 底图冻结 + 逐像素一致 + 置顶窗口不穿透（三道防护见 §3.2） |
| `verify-clipboard.ps1 <exe>` | 剪贴板图尺寸精确 + alpha + 无残留进程 |
| `verify-rewarm.ps1 <exe>` | 热身失效后自动重热（含监听窗口广播资格） |
| `probe-zorder.ps1 <exe> [nostyle]` | 直接读底图窗口 `GWL_EXSTYLE` 和 z 序邻居 |
| `shoot-overlay.ps1 <exe> [out.png]` | 把遮罩截下来人眼看 |
| `lib.ps1` | 公共：`Reset-Chenocr` 清残留进程、`Assert-Hotkey` 查热键、`Set-ChenocrEnv` |
| `generate-icons.mjs` | 图标不入库，按数学定义画出来 |

需要 `-STA` 的脚本（用了剪贴板或 WinForms）：`verify-clipboard.ps1`、
`verify-backdrop.ps1`、`shoot-overlay.ps1`。

**跑之前先 `Reset-Chenocr`。** 残留进程会占着 F1 热键，导致新起的进程注册失败，
而脚本会照跑并给出**看着合理但完全无意义**的结果。踩过。

### 4.4 Clippy

```powershell
cargo clippy --all-targets          # 已配置 deny(unwrap_used, expect_used)
```

配置在 `src-tauri/src/lib.rs` 顶部：

```rust
#![deny(clippy::unwrap_used, clippy::expect_used)]
#![cfg_attr(test, allow(clippy::unwrap_used, clippy::expect_used))]
```

测试代码整体放行（断言失败就该 panic）。注意 `cfg_attr(test, ..)` 是**整个 crate**
放行，所以生产代码的拦截发生在非 test 那次编译上；`--all-targets` 两次都编，覆盖
完整。已验证 lint 真的生效（往生产代码塞一个 `unwrap()`，clippy 报错中止编译）——
**配错了的 lint 比没有 lint 更危险**，改动这段配置后请重做这个验证。

## 5. 踩过的坑

### 5.1 已修

| 症状 | 根因 | 解法 |
|---|---|---|
| 按 F1 遮罩不出现，无任何报错；此后每次 F1 都没反应 | 前端 `fetch('shot://...')` 被 CSP 静默拦成 "Failed to fetch"；异常抛出后**会话没回收**，之后全被"已在截图中"挡掉 | CSP `connect-src` 补 `shot: http://shot.localhost`；失败路径补 `captureCancel()`（§3.6）；加 `reportError` 通道 |
| 同上 | 自定义协议响应缺 `Access-Control-Allow-Origin`，跨源被拒 | 协议响应加 `Access-Control-Allow-Origin: *` |
| 按 F1 后遮罩永远不出现，页面里 JS 完全不跑，无报错 | 在 `setup()` 里创建的窗口拿不到 Tauri 注入的 IPC 初始化脚本 | 预建移到 `RunEvent::Ready` |
| 剪贴板图 600×450，应该是 400×300 | 脚本是 DPI-unaware 的，坐标被系统虚拟化（150% 屏上 ×1.5） | 脚本先调 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` |
| **把显示器规格记错成 1440p** | 同上：DPI-unaware PowerShell 把物理 3840×2160 报成逻辑 2560×1440。据此写进文档的"4K 双屏会爆预算"其实是**已测环境** | 用 DPI-aware 查询确认 3840×2160 @144 DPI；文档全部改正 |
| 首次 F1 比后续慢 90ms | 首次抓屏建 D3D 设备 + 开 WGC 会话，137ms vs 热态 49ms | 启动后台线程空跑一次（§3.3） |
| 底图透明/发黑 | GDI/WGC 抓到的图 alpha 全 0 | 先强制 alpha=255，后改 24bpp BMP 从根上绕开 |
| 抓屏 260–370ms | xcap 默认走 GDI 路径 | 开 `wgc` feature |
| `verify-backdrop.ps1` 时过时不过 | **脚本自己**在取基准和按 F1 之间 `Write-Host`，滚动了压在比对区的终端 | 输出攒到比对后再打 + 静默沉降期（§3.2d） |
| 置顶穿透测试永远绿灯 | 入侵者是普通窗口，到不了那个夹层 | 改成 F1 前就存在的 topmost 窗口 + `SWP_NOZORDER`（§3.2b/c） |
| `verify-backdrop.ps1` 杀不掉 notepad | Win11 记事本是 Store 应用，`Start-Process -PassThru` 拿到的进程立刻退出 | 改成自建 WinForms 窗口（顺带解决了拿不到句柄的问题） |
| 脚本报 `MissingEndCurlyBrace`，位置毫无道理 | 缺 UTF-8 BOM，中文按 ANSI 解释破坏词法 | 所有 `.ps1` 存 BOM（§3.12） |
| `pnpm install` 退出码 1 | `[ERR_PNPM_IGNORED_BUILDS]`，esbuild 的 postinstall 被忽略 | `pnpm-workspace.yaml` 里 `allowBuilds: esbuild: true` |
| 热键被占，脚本仍给出"正常"结果 | 残留 `chenocr` 进程占着 F1 | `Reset-Chenocr` + `Assert-Hotkey` |
| GUI 进程初始化失败时"双击了没反应"，无任何线索 | `windows_subsystem = "windows"` 没有控制台，panic 信息进虚空 | 改 `match` + 写日志 + `exit(1)` |

## 6. 性能基线

### 6.1 测试硬件

**单显示器 3840×2160 @ 150% 缩放（144 DPI）。** 这一条很重要：它同时覆盖了规格 08
要求的"单屏 150% 缩放"和"4K 单屏"两种环境。

> 曾把它误记成 2560×1440 —— DPI-unaware 的 PowerShell 报的是逻辑分辨率。
> 量任何坐标/尺寸之前先声明 PMv2。

### 6.2 实测数字（release 构建）

| 指标 | 数字 |
|---|---|
| 热键 → 画面可见（首次） | **79ms** |
| 热键 → 画面可见（后续） | **67–73ms** |
| 其中抓屏（热态） | 48–53ms |
| 其中底图上屏 `show_ms` | 11–16ms |
| 抓屏（冷态，无热身） | 137ms |
| 热键 → 底图像素进 WebView | 236–258ms（fetch 143–167ms + decode 24–26ms） |
| 底图 payload（24bpp BMP） | 24.9 MB |
| BMP 编码 | ~6ms |
| NSIS 安装包 | 1.83 MB |
| exe | 5.52 MB |

预算：热键到可见 150ms（规格 00 §6.4）、M0 放宽到 200ms（规格 08）。**当前有 2 倍余量。**

像素进 WebView 那 236–258ms 不在关键路径上：画面 70ms 就出来了，这些像素只供
放大镜/取色/马赛克用，到位前那几个工具不渲染。用户从看见画面到手开始动至少
200–400ms，感知不到。

### 6.3 被否决的方案（别重做一遍）

| 方案 | 实测 | 结论 |
|---|---|---|
| 底图当图片喂 WebView | 全链路 244ms | 传输是"74ms 固定 + 2.4ms/MB"，随像素数线性涨，且 Chromium 色彩管理会改像素值 |
| PNG（Fast + NoFilter） | 编码 100ms+，**体积比 BMP 还大** | 桌面截图压不动 |
| 32bpp BMP | 33.2 MB | 多传 25% 的无用 alpha，改 24bpp 后 24.9 MB |
| `arrayBuffer` → `Blob` 再解码 | 多一次 33MB 拷贝 | 改成直接 `response.blob()` |
| DXGI 常驻 warm session | 未做 | 启动热身已把首次 F1 降到 79ms，单屏用不上。双屏超预算时再考虑 |

### 6.4 未测

- **双屏任何数字。** 抓屏逐块进行、底图每块屏各自一次 `UpdateLayeredWindow`，
  两条都随屏数涨。**不要外推单屏的 79ms。**
- **双 4K。** 规格 08 列为必测环境。
- 混合 DPI（主 150% + 副 100%）下的坐标正确性。
- 副屏负坐标。
- 拖拽帧率（拖拽逻辑本身 M0 只有最小实现，60fps 是 M1 的事）。

## 7. 环境与命令

### 7.1 前置依赖

- Node 20+（实测 v24.19.0）
- Rust 1.82+ MSVC toolchain（实测 1.97.0）
- Windows 10 2004+（`WDA_EXCLUDEFROMCAPTURE` 和 WGC 抓屏都要这个版本以上）

### 7.2 命令

```powershell
corepack pnpm install                      # 装依赖
corepack pnpm tauri dev                    # 开发
corepack pnpm tauri build --no-bundle      # 只出 exe，跑验收脚本用这个
corepack pnpm tauri build                  # 出 NSIS 安装包

corepack pnpm test                         # 前端 18 个测试（选区几何/坐标换算）

cargo clippy --all-targets                 # 已配 deny(unwrap_used, expect_used)
corepack pnpm lint                         # ⚠ 报错退出，配置不存在（§5.2）
```

真机抓屏烟雾测试要有物理显示器，默认 `#[ignore]`。手动跑会打印各显示器几何、
缩放比例和分段耗时 —— **排查 DPI 和性能问题先看这个**：

```powershell
cargo test --manifest-path src-tauri/Cargo.toml -- --ignored --nocapture
cargo test --profile perf --manifest-path src-tauri/Cargo.toml -- --ignored --nocapture
```

`perf` 档位和 release 同样开优化但不做全量 LTO，重编快得多，量性能用它。

**注意**：`cargo build` / `cargo test` 的产物目录被环境重定向到
`%LOCALAPPDATA%\Temp\cursor-sandbox-cache\<hash>\cargo-target\`，不是
`src-tauri/target/`。脚本要传 exe 路径时以构建输出里打印的那行为准。

另外：**app 在跑的时候 build 会失败**（`拒绝访问 (os error 5)`，exe 被占用）。
先 `Reset-Chenocr`。

### 7.3 代码结构里几个不明显的地方

- **平台相关代码只允许出现在 `src-tauri/src/platform/`**。这一层之外禁止
  `#[cfg(windows)]`、禁止 `use windows::`、trait 签名里禁止出现 `HWND`/`HMONITOR`
  （句柄包 `u64`）。理由见规格 07 §1，这是 macOS 移植的前提。
- **冻结底图不进 WebView**，是独立的原生分层窗口，和透明遮罩由 DWM 合成，两者用
  `DeferWindowPos` 原子上屏。见 `platform/mod.rs` 的 `BackdropLayer` 文档。
- **遮罩窗口启动时就建好并隐藏**，热键路径上只 `show`。
- **选区状态一律存虚拟桌面物理像素**，只在渲染时换算成 CSS 像素。混合 DPI 多屏下
  反过来做会累积误差。

## 8. 下一步

### 8.1 顺序（用户已定）

**第一步：人工观感验证（不要跳过）。**

用户的原话：M0 的数值那一半答完了，"Tauri 做的遮罩用起来像不像原生工具"这一半
没人验过，且只有人能验 —— 这是重新考虑选型成本最低的最后一刻。

跑起来：`corepack pnpm tauri build --no-bundle` 然后直接运行 exe（正常模式，
不要设任何诊断环境变量），按 F1。检查点见 §1.3。

**第二步：补 ESLint 配置。** 见 §5.2，三条必开规则都有对应的真实事故。

**第三步：硬件到货后立刻重测双屏。** 优先于任何 M1 功能。要测：
1. 热键到可见延迟（§6.4）
2. 混合 DPI（主 150% + 副 100%）背景正确、不错位、不模糊
3. 副屏负坐标

若双屏超预算，再评估 DXGI 常驻 warm session。

**第四步才是 M1。** 读 `docs/spec/02-截图模块.md`。

### 8.2 为什么不能先进 M1

用户明确否决过"先进 M1、双屏等硬件到了再验"：

> M1 头三件事（窗口枚举、自动检测、放大镜）全是坐标密集型，正是混合 DPI 最容易崩
> 的部分，在未验证的坐标地基上盖两三周代码就是 M0 要防的失败模式。

### 8.3 接手时先读什么

1. 本文件 §3（不能删的东西）—— 否则很容易"顺手清理"掉关键代码
2. `src-tauri/src/platform/mod.rs` 的 `BackdropLayer` 文档 —— 架构决策的完整理由

4. `src-tauri/src/capture/mod.rs` 文件头 —— 为什么整条链路由 Rust 驱动
