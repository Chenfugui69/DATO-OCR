## 3. 两处关键冲突及其化解（重点，接手方需重点复核）

### 3.1 Electron ↔ 体积小巧

用户第一轮选了 Electron，这与他自己写在第一句的"体积小巧"直接冲突。

**处理方式**：没有直接驳回，而是先做了三组网络检索取证，把证据摆出来让用户重新选。

**取到的关键证据：**

1. **体积实测**（同一产品的两个版本，Tabularis vs Beekeeper Studio）：
   - Windows 安装包 Tauri 12 MB / Electron 201 MB
   - macOS dmg 18 MB / 290 MB
2. **运行时实测**：空闲内存 42 MB / 187 MB，冷启动 380 ms / 1420 ms
3. **推翻 Electron 唯一实质优势的证据**：
   - `react-screenshots`（最像微信的开源截图 UI，含马赛克/文字/画笔/箭头/椭圆/矩形）是**独立的 React 组件，不绑定 Electron**
   - 抓屏内核 `xcap` 是 Rust 库，`electron-screenshots` 依赖的 `node-screenshots` 就是它的 Node 绑定，`tauri-plugin-screenshots` 也基于它 —— **两边同源，作者同为 nashaofu**
4. **同形态的 Tauri 实例已存在**：
   - EcoPaste（Tauri v2 剪贴板管理器，对标 Paste，安装包 7.3 MB，Apache-2.0）
   - **WeCut**（在 EcoPaste 上加了截图标注 + OCR + 贴图钉屏，形态与 CHENOCR 几乎一致）
   - Snow Shot（Tauri 截图工具）

**结论**：用户在第二轮改选 Tauri。这是整个方案里最关键的一次翻转。

**留给接手方的问题**：Electron 剩余的两条真实优势（构建速度快、疑难杂症资料多）是否被低估？特别是 Rust 全量编译 18 分钟 vs Electron 4 分钟这个数据，对一个 10 周的项目意味着什么。

### 3.2 "完全照抄微信" ↔ 要加的四个功能

用户选了"工具条一个多余按钮都不加"，但同时要求 OCR、翻译、长截图、贴图。这四个功能在微信截图里都不存在，没地方放。

**处理方式**：指出矛盾，让用户在第二轮重新界定。用户确认"抄的是手感，工具条可以加图标"。

**落地方式**：`02-截图模块.md` 把"微信手感"拆成了 **60 多条带勾选框的验收项**（遮罩透明度 0.45、无淡入动画、窗口自动检测、放大镜 6 倍、8 个控制点、工具条右对齐选区下方、Enter/Esc/右键/双击的行为等），工具条在微信原有 10 个按钮后追加 4 个新图标。

## 4. 最终锁定的技术方案

```
Tauri v2 + React 18 + TypeScript + Vite 6
Tailwind CSS 4 + Radix UI Primitives（无样式，自套苹果皮）
Zustand + TanStack Query + TanStack Virtual
Rust: xcap(抓屏) / clipboard-rs / window-vibrancy / rusqlite+FTS5 / imageproc(拼接)
OCR: RapidOCR-json 作为 sidecar 子进程（30MB），PaddleOCR 可选下载（250MB）
```

| 维度 | 结论 | 数字 |
|---|---|---|
| 安装包目标 | ≤ 40 MB | 硬红线 |
| 空闲内存 | ≤ 80 MB | 硬红线 |
| F1 到遮罩可交互 | ≤ 150 ms | 硬红线，**当前实测未达标，见 §7** |
| 冷启动到托盘 | ≤ 800 ms | 硬红线 |
| 工期 | 约 10 周（M0–M7） | 估算，未验证 |

**8 条写进文档的铁律**（不允许实现方自行更改）：框架必须 Tauri、截图必须逐项对齐微信、UI 必须 Apple 且禁用 Ant/Material 类组件库、禁止 GPL/AGPL 依赖、长截图只做手动、剪贴板默认全量记录、OCR 默认 RapidOCR、禁止直接抄闭源软件代码。

## 6. 方案中带有主观判断、需要复核的部分

以下是我（方案制定方）自己认为**证据不够硬或存在争议**的地方，接手方应重点审视：

### 6.1 设计库输出被我推翻

调用了本地的 UI/UX 设计库（`ui-ux-pro-max`）生成设计系统，它返回的是**青绿 #0D9488 + 橙 #EA580C 的配色、Plus Jakarta Sans 字体、"Minimal Single Column"落地页版式**。这套东西是给营销落地页用的，与苹果桌面软件完全不搭。

**我的处理**：只保留它的动效曲线、玻璃效果参数和交付前检查清单，配色/字体/版式全部替换为苹果 HIG 的真实数值（systemBlue `#007AFF`/`#0A84FF`、label 层级、0.5px 分隔线、13px 正文等）。

**需要复核**：我写进 `06-UI设计规范.md` 的苹果数值是凭知识给出的，没有逐个对照官方 HIG 文档核验。特别是深色模式的一组 `rgba` 值和 Text Style 的字号映射，建议抽查。

### 6.2 字体授权

方案要求**内嵌 MiSans** 并子集化到 2.5 MB，理由是 Windows 上没有苹方，fallback 到微软雅黑会让苹果味完全消失。

**风险**：我在文档里写的是"小米开源，免费商用"。这个说法的**具体授权条款我没有逐字核验**。闭源商业分发前必须去读 MiSans 的实际许可证，确认是否允许嵌入到闭源软件中分发。如果不允许，备选是 HarmonyOS Sans SC（同样需核验）或思源黑体（SIL OFL，明确允许）。

### 6.3 免费翻译接口

方案内置有道 / Bing / Google 三个**非官方网页接口**做降级链。

**风险两条**：稳定性（随时可能失效，已在文档里要求收敛到单个目录便于替换）和**合规性**（用非官方接口做商业分发是否有问题，我没有评估）。

### 6.4 用户的两个选择带来的实质风险

这两条是用户明确拍板的，我按要求执行了，但接手方值得知道代价：

**剪贴板全量记录**：意味着密码管理器复制出来的密码会明文躺在本地 SQLite 里。我加了一个默认关闭的应用黑名单开关作为后门，并要求在关于页明确告知用户数据存储位置和加密状态。但默认行为的风险是真实的。

**长截图只做手动滚动**：兼容性最好，但相比 PixPin/Snipaste 的自动滚动是功能上的减配。用户选这个的理由是"自动滚动经常拼歪"，成立，但竞品差距要接受。

### 6.5 工期与性能红线是估算

10 周的排期和 150ms/80MB/40MB 这些红线数字，**都是我基于经验拍的，没有基线实测支撑**。`react-screenshots` fork 改造能省 1–2 周这个判断也未经验证。见 §7 —— 已经有一个红线被实测打脸了。

### 6.6 法律边界

"对齐微信交互但不抄代码"是行业通行做法，我在铁律里写死了禁止直接复制闭源软件代码、禁止引入 GPL/AGPL（因为要闭源发布，Flameshot 是 GPL-3.0 已明确排除）。但"交互设计的相似度到什么程度算侵权"这件事我没有能力判断，仅作了工程层面的隔离。

## 7. 方案定稿后的实测反馈（来自并行的实现会话）

方案交付后，实现方 AI 已开始跑 M0 技术验证，用户把两次进度截图拿来征询意见。这部分是**对方案的第一批真实反馈**，很重要。

### 7.1 已达成

- 前端 18 个测试、Rust 10 个测试通过
- 剪贴板复检 400×300 精确、alpha 不透明、无残留进程
- 修掉三个静默失败：CSP `connect-src` 拦 fetch、自定义协议跨源缺 CORS 头、底图失败时会话不回收导致后续 F1 全被"已在截图中"挡掉
- 加了 `report_error` 通道把前端异常写进 Rust 日志（遮罩窗口既隐藏又无 devtools，是全项目最深的调试盲区）

### 7.2 **红线被打脸：F1 到可交互实测 450 ms，方案红线是 150 ms**

其中抓屏本身占 118 ms。

实现方提出的方案是换本地回环 HTTP 传输（预期降到 50ms）或者改用原生底图层。

**我给出的意见**（用户已采纳）：

> 450ms 还没被拆开，A 和 B 都只解决传输、没解决编码。2560×1440 RGBA 是 14.7 MB，Rust `image` crate 默认参数压 PNG 本身就要 150–400 ms，很可能占了一多半。只换传输通道会停在 200ms 出头。
>
> 按性价比排：(1) 先埋点拆出 抓屏/编码/传输/解码/首帧 五段耗时；(2) PNG 编码器改 `CompressionType::Fast + FilterType::NoFilter`，一行改动通常砍 3–5 倍；(3) 还不够就别用 PNG —— 遮罩底图用完即丢，没有压缩必要，改 BMP 编码约等于 memcpy，代价是搬 15–30 MB，交给回环 HTTP；(4) 抓屏 118 ms 也不正常，DXGI Desktop Duplication 抓一帧应在 5–16 ms，说明每次都在重新初始化复制会话，改成常驻 warm session。
>
> 原生底图层（透明 WebView2 + 原生层画底图）是终局解法，Snipaste/PixPin 都这么干，但它正是 WebView2 已知问题最集中的地方。留作后手，前四步做完还超 150ms 再动。

**给接手方的问题**：如果四步做完仍然进不了 150 ms，是该放宽红线，还是该走原生底图层，还是该重新评估 Tauri？这是目前最大的未决风险。

### 7.3 混合 DPI 测试环境

实现方要装虚拟显示器驱动来模拟混合 DPI，提供了 Parsec VDD（WHQL 签名）、itsmikethetech VDD（需开测试签名）、用户自装、推迟到 M1 四个选项。

**我给出的意见**（用户已采纳）：

> 推迟到 M1 绝对不行 —— 混合 DPI 是全项目风险最高处，M0 存在的唯一意义就是在投入两三周前把可能推翻技术选型的问题撞出来。
>
> 但也不用装驱动：**HDMI 诱骗器**（EDID 模拟器，淘宝十几块）插上就是一块真实第二显示器，零驱动、零权限、不碰显示栈，分辨率和缩放独立可调，也能拖到主屏左边制造负坐标。等一天快递，换一套长期可用的干净测试环境。手边有第二台 Windows 或安卓平板的话，Miracast 立刻可用。
>
> 事实修正：Parsec VDD 是 **IddCx 用户模式**驱动，不是提问里说的内核模式。
>
> 单显示器 150% 缩放的测试现在就能跑，不需要第二块屏，能抓出 DPI 感知缺失、scale factor 写反、canvas 没用物理像素这类问题，也就是混合 DPI 故障的大多数。
>
> 保留：虚拟显示器在 DXGI Desktop Duplication 下一般正常但非百分百，虚拟屏上发现的异常要在真实屏复现后才算数。

## 9. 希望接手方重点分析的几个问题

按重要性排序：

1. **§7.2 的性能问题是否动摇了 Tauri 选型**？450ms 里如果编码和传输都优化到极限仍进不了 150ms，方案的应对是什么？我给的四步优化路径判断是否正确（尤其"PNG 编码占大头"这个推断，它决定了优化顺序）？

2. **10 周工期是否现实**？特别是 M1 截图核心给了 2–3 周、M4 剪贴板给了 2 周，考虑到 Rust 编译等待时间，这个估算是否乐观？

3. **`react-screenshots` 走 fork 改造（路线 A）而非重写（路线 B）是否正确**？它是微信风视觉、需全部重写样式，且不含窗口自动检测、放大镜、贴图。"省 1–2 周"这个判断是否站得住？

4. **§6.2 的字体授权**必须在分发前落实，这是唯一一个可能导致法律问题的硬缺口。
